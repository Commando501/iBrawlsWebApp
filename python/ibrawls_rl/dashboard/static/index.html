The 30-second mental model

          
You don't program tactics. You set the reward (what counts as "good") and the
          opponent, then the bot discovers tactics by playing millions of ticks and nudging
          its brain so future reward goes up. A match from start to win/timeout is an
          episode. Training = play, measure, nudge, repeat.

          
Workflow: edit Settings on the Train tab → Start training →
          watch the Live progress charts → Evaluate a saved brain for a real grade →
          adjust and run the next stage.

        


        

          
Reading the charts what each output means & the range you want

          
These are the live-progress / run-comparison charts. Watch the
          trend, not a single number. Reward magnitudes depend on your reward weights, so a
          rising line matters more than its absolute height.

          

            
ChartWhat it meansWhat you want

            
              

                Win rate vs opponent
eval/win_rate		
                Fraction of grading matches the bot won (0–1). During a self stage it's
                still measured vs random as a steady yardstick.
                > 0.9 before advancing a stage. 0.6 = undertrained,
                give it more steps.
              

              

                Episode reward
rollout/ep_rew_mean		
                Average total reward per match. The headline "is it learning?" line.
                Trending up. Plateau = converged (or stuck).
              

              

                Eval episode return
eval/ep_return		
                Average reward in the dedicated grading matches — a cleaner signal than the
                rollout reward.
                Rising, then plateauing high.
              

              

                Episode length
rollout/ep_len_mean		
                Average match length in ticks.
                Falling = decisive wins. Stuck high = stalling /
                can't close out.
              

              

                Explained variance
train/explained_variance		
                Can the bot predict how a match will turn out?
                Rising toward 1.0. Negative = value predictor
                failing → lower learning rate.
              

              

                Entropy (exploration)
train/entropy_loss		
                How random the bot still is. Starts around −6.5.
                Drifting slowly toward 0. Pinned at the start = not
                committing; crashes to 0 early = stopped exploring too soon.
              

              

                Policy change (KL)
train/approx_kl		
                How much the brain moved in one update.
                ~0.005–0.03. Much bigger = unstable → lower learning
                rate or clip range.
              

              

                Value loss
train/value_loss		
                Error in predicting future reward.
                Gradually decreasing; brief spikes when reward scale shifts
                are normal.
              

              

                Policy / total loss
train/policy_gradient_loss, train/loss		
                PPO's internal objectives — not like a supervised loss.
                No clean target; jittery is fine. Don't chase these.
              

              

                Speed
time/fps		
                Environment steps per second (throughput). CPU-bound on the sim.
                As high as your cores allow; raise num_workers /
                parallel_matches to lift it.
              

            
          

        


        

          
The reward trap read this before tuning rewards

          
The bot does exactly what pays best — the reward is the strategy.
          Dense rewards add up over thousands of ticks: possession = 0.002 per
          tick held for 1800 ticks pays 3.6 — more than scoring a goal (1.0) or
          winning (1.0). So if dense terms are too big, the bot hoards the ball forever
          instead of scoring.

          
    
            
  • Sparse (win, goal_scored, goal_conceded) = the true goal.
    • 
            
  • Dense (possession, ball_progress, kill, death, approach, time_penalty) =
            hints that speed up early learning but mislead if too strong.
    • 
          

          
Common fix: start with dense rewards a bit larger to learn the basics
          fast, then shrink them in a later run so the bot optimizes the real objective
          (winning).

        


        

          
Running the stages the curriculum: easy → hard

          
Train in stages, each warm-started from the previous one (set
          network → init_model to the prior stage's final_model.zip). Keep
          width/depth identical across stages or the weights won't transfer.
          Don't advance until a stage is actually good (> 0.9 win rate, not 0.6).

          

            
StageSettingsGoal before moving on

            
              

                1 · vs random
                opponent = random, init_model = "" (from scratch),
                ~3M+ steps.
                win_rate plateaus high (>0.9), entropy falling, explained_variance
                rising.
              

              

                2 · self-play
                opponent = self, init_model = stage 1's final model. Bot invents
                its own counters.
                win_rate (still vs random) stays high; reward keeps climbing.
              

              

                3 · vs heuristic
                opponent = heuristic, init_model = stage 2's final model.
                This is the final exam — the scripted bot is near-shutout. Even a strong
                base finds it hard; treat any solid win rate as a win.
              

              

                4 · harden (optional)
                randomize → enabled = true, pct ≈ 0.15, init_model =
                stage 3. Trains across a band of balance settings.
                Survives live balance patches; expect a temporary dip while it re-stabilizes.
              

            
          

          
Combat mode is separate: it always self-plays a mix of match
          sizes — no opponent setting. You end up with two brains (one grifball, one combat); load
          whichever matches the live game mode.

          
Stuck at win_rate ≈ 0? The from-scratch brain never reaches the
          action. Shorten matches (match_minutes = 1.0, goal_target = 1) and raise
          reward → approach to 0.05 so it gets pulled toward the ball/enemy, then lengthen
          matches once it's winning.

        


        

          
Naming your run directories

          
Each run writes to its own logging → dir. Always give every stage / experiment
          its own folder — runs sharing a folder overwrite each other's checkpoints and tangle
          the charts. The Runs tab lists each folder and lets you tick several to compare.

          
Recommended pattern: runs/<stage>_<what> — short, sortable,
          self-describing:

          

            
FolderMeaning

            
              
runs/s1_randomStage 1, grifball vs random.

              
runs/s2_selfStage 2, self-play (continues s1).

              
runs/s3_heurStage 3, vs heuristic (continues s2).

              
runs/s4_drStage 4, domain-randomized hardening.

              
runs/combat_v1Combat generalist, first attempt.

              
runs/s1_random_lr5e4Variant: append the knob you changed
              when sweeping (e.g. learning rate) so comparisons are obvious.

            
          

          
Tips: prefix with s1_/s2_ so stages sort in order; keep names
          lowercase with underscores (no spaces); when re-running an experiment, bump a suffix
          (_v2) rather than reusing a folder.
