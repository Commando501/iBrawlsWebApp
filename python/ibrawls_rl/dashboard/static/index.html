The 30-second mental model combat is the focus

          
You don't program tactics. You set the reward (what counts as "good"), then the
          bot discovers tactics by playing millions of ticks and nudging its brain so future reward
          goes up. A round from start to win/timeout is an episode. Training = play, measure,
          nudge, repeat.

          
Workflow: edit Settings on the Train tab (mode is
          combat) → Start training → watch the Live progress charts →
          Evaluate the saved brain (mode = combat) for a real grade → optionally harden with
          domain randomization.

          
Grifball mode exists but isn't the current focus. Everything below
          is written for combat; the grifball curriculum is kept at the bottom for reference.

        


        

          
Combat training your main path

          
Combat trains one generalist that handles 1v1, free-for-all, and team deathmatch
          at any kill total. It does this by self-playing a mix of match sizes at once and
          re-randomizing the teams each episode — that variety is what makes one brain generalize.
          There's no opponent setting: every agent in every match is the learner.

          

            
KnobWhat it doesTip

            
              
[combat] world_sizes
                The fixed sizes of the parallel matches. 2 = a 1v1; 4/8
                = FFA or teams.
                The mix is the generalization. Bias toward more 2s early for a
                faster, cleaner learning signal.

              
[combat] kill_min / kill_max
                Per-episode kill target is sampled in this range.
                Lower kill_min early so rounds end sooner → more episodes → faster
                learning.

              
[combat] randomize_layout
                Re-randomize team partition + kill target every episode.
                Keep on for a true generalist.

              
[run] match_minutes
                Hard timeout per round.
                Keep short (≈ 1.0–1.5) so rounds resolve instead of timing out.

              
[randomize] enabled / pct
                Jitter the game mechanics ±pct each episode.
                Leave off for the first run (learn the core skill), then a 2nd warm-started
                run with enabled = true, pct = 0.15 to survive balance patches.

            
          

          
The combat loop: (1) train one run from scratch (e.g.
          runs/combat_v1) until reward plateaus and episode length stops falling;
          (2) grade it on the Evaluate tab with mode = combat (it duels 1v1 vs random);
          (3) optionally warm-start (network → init_model) into a domain-randomized hardening
          run. Usually one self-play run + optional DR — no multi-opponent curriculum.

          
Combat ignores the grifball-only knobs entirely (opponent,
          goal_target, parallel_matches), so don't bother tuning those here.

        


        

          
Reading the charts what each output means & the range you want

          
These are the live-progress / run-comparison charts. Watch the
          trend, not a single number. Reward magnitudes depend on your reward weights, so a
          rising line matters more than its absolute height.

          
In combat there's no live eval/win_rate or
          eval/ep_return — combat self-plays with no fixed opponent to grade against
          mid-run, so those two charts only appear for grifball. Judge a combat run by
          rollout/ep_rew_mean rising + rollout/ep_len_mean falling, then a
          real grade on the Evaluate tab.

          

            
ChartWhat it meansWhat you want

            
              

                Episode reward
rollout/ep_rew_mean		
                Average total reward per round. The headline "is it learning?" line — your
                primary combat signal.
                Trending up. Plateau = converged (or stuck).
              

              

                Episode length
rollout/ep_len_mean		
                Average round length in ticks.
                Falling = decisive fights. Stuck high = passive / not
                committing to kills.
              

              

                Win rate vs opponent (grifball only)
eval/win_rate		
                Fraction of grading matches won (0–1). Not produced in combat.
                > 0.9 before advancing a grifball stage.
              

              

                Eval episode return (grifball only)
eval/ep_return		
                Average reward in the grifball grading matches. Not produced in combat.
                Rising, then plateauing high.
              

              

                Explained variance
train/explained_variance		
                Can the bot predict how a match will turn out?
                Rising toward 1.0. Negative = value predictor
                failing → lower learning rate.
              

              

                Entropy (exploration)
train/entropy_loss		
                How random the bot still is. Starts around −6.5.
                Drifting slowly toward 0. Pinned at the start = not
                committing; crashes to 0 early = stopped exploring too soon.
              

              

                Policy change (KL)
train/approx_kl		
                How much the brain moved in one update.
                ~0.005–0.03. Much bigger = unstable → lower learning
                rate or clip range.
              

              

                Value loss
train/value_loss		
                Error in predicting future reward.
                Gradually decreasing; brief spikes when reward scale shifts
                are normal.
              

              

                Policy / total loss
train/policy_gradient_loss, train/loss		
                PPO's internal objectives — not like a supervised loss.
                No clean target; jittery is fine. Don't chase these.
              

              

                Speed
time/fps		
                Environment steps per second (throughput). CPU-bound on the sim.
                As high as your cores allow; in combat raise num_workers
                toward your core count (and widen [combat] world_sizes) to lift it.
              

            
          

        


        

          
The reward trap read this before tuning rewards

          
The bot does exactly what pays best — the reward is the strategy.
          Dense rewards add up over thousands of ticks, so a small per-tick payout can quietly
          out-earn the real objective. In combat the dense term to watch is approach
          (paid per metre closing on the nearest enemy): if it's too large the bot learns to
          hug enemies for the shaping bonus instead of committing to kills.

          
    
            
  • Sparse / true goal (combat): kill, death,
            win — what you actually want it to optimize.
    • 
            
  • Dense hints (combat): approach, time_penalty — a
            foothold that gets a fresh brain moving toward fights, but misleading if too strong.
    • 
            
  • Grifball-only (ignored in combat): possession,
            ball_progress, goal_scored, goal_conceded.
    • 
          

          
Combat rule of thumb: keep approach small (≈0.03–0.05) as an
          early foothold and make sure kill clearly out-pays it, so the bot graduates
          from "approach enemies" to "actually kill them". Shrink approach in a later
          warm-started run if it stays passive.

        


        

          
Human-like play decision interval & behavior stats

          
[run] decision_interval is the single most important knob for the
          human-like goal. At 1 the bot re-decides 60 times a second — super-human
          twitch reactions and 5× slower training. At 5 it decides ~12×/sec, which is a
          human reaction cadence (~80–200ms), and training throughput multiplies by ~5.
          Train and evaluate at the same value (the Evaluate tab reads it from the run
          automatically).

          
Every evaluation now also reports behavior stats — idle %, move-switch rate
          (twitchiness), attack/jump/dash usage — and the trainer logs them live under
          behavior/*. Watch move_switch_rate: humans hold a direction
          (≲0.3); a jittery policy flips most decisions (≳0.5). The Advisor flags it.

          
With frame-skip, gamma is per decision: at interval 5,
          gamma = 0.99 covers the same time horizon the old 60Hz 0.997 did.

        


        

          
The Optimizer tab hardware presets + knob sweeps

          
Your machine detects CPU/RAM/GPU and proposes settings sized to keep the GPU fed
          (workers ≈ threads − 4, ~3 worlds per worker, big rollout buffers). One click applies them
          to the Train settings.

          
Sweep builder answers "which learning rate / entropy / kill reward is best?"
          empirically: pick the knob, list candidate values, and it queues one short probe run per
          value. The queue runs them back-to-back overnight; the results table shows final
          reward / win rate per value, highlights the best, and "Use config" promotes the winner.
          Probe with ~2M steps — enough to rank values, cheap enough to try five.

        


        

          
Grifball curriculum secondary — skip unless you train grifball

          
Not the current focus. Combat (above) is a single self-play run, not
          a multi-opponent curriculum, and ignores every knob in this card. Keep reading only if you
          deliberately want a ball-carrying grifball bot.

          
Train in stages, each warm-started from the previous one (set
          network → init_model to the prior stage's final_model.zip). Keep
          width/depth identical across stages or the weights won't transfer.
          Don't advance until a stage is actually good (> 0.9 win rate, not 0.6).

          

            
StageSettingsGoal before moving on

            
              

                1 · vs random
                opponent = random, init_model = "" (from scratch),
                ~3M+ steps.
                win_rate plateaus high (>0.9), entropy falling, explained_variance
                rising.
              

              

                2 · self-play
                opponent = self, init_model = stage 1's final model. Bot invents
                its own counters.
                win_rate (still vs random) stays high; reward keeps climbing.
              

              

                3 · vs heuristic
                opponent = heuristic, init_model = stage 2's final model.
                This is the final exam — the scripted bot is near-shutout. Even a strong
                base finds it hard; treat any solid win rate as a win.
              

              

                4 · harden (optional)
                randomize → enabled = true, pct ≈ 0.15, init_model =
                stage 3. Trains across a band of balance settings.
                Survives live balance patches; expect a temporary dip while it re-stabilizes.
              

            
          

          
Stuck at win_rate ≈ 0? The from-scratch brain never reaches the
          action. Shorten matches (match_minutes = 1.0, goal_target = 1) and raise
          reward → approach to 0.05 so it gets pulled toward the ball, then lengthen
          matches once it's winning.

        


        

          
Naming your run directories

          
Each run writes to its own logging → dir. Always give every stage / experiment
          its own folder — runs sharing a folder overwrite each other's checkpoints and tangle
          the charts. The Runs tab lists each folder and lets you tick several to compare.

          
Recommended pattern: runs/<stage>_<what> — short, sortable,
          self-describing:

          

            
FolderMeaning

            
              
runs/combat_v1Combat generalist, first run (from scratch).

              
runs/combat_v2Next attempt / continued run (warm-started from v1).

              
runs/combat_drDomain-randomized hardening run (continues a combat_vN).

              
runs/combat_v2_lr1e4Variant: append the knob you changed
              when sweeping (e.g. learning rate) so comparisons are obvious.

              
runs/s1_random …Grifball stages (secondary):
              s1_random → s2_self → s3_heur → s4_dr.

            
          

          
Tips: keep names lowercase with underscores (no spaces); when re-running an
          experiment, bump a suffix (_v2) rather than reusing a folder; append the swept
          knob (_lr1e4) so the Runs-tab comparison is self-explaining. (The Evaluate tab's
          Apply button auto-bumps the dir to a fresh _vN for you.)
